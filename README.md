# energoreestr

Відкриті реєстри НКРЕКП з data.gov.ua, зібрані в одну базу з пошуком за ЄДРПОУ, історією змін і звітом про якість самих файлів. Стане в пригоді, якщо треба швидко побачити, що ці реєстри знають про компанію на енергоринку, або якщо ви самі розбираєте ці файли і хочете знати, де в них пастки.

**Пошук наживо: [maksym-garkusha.github.io/energoreestr](https://maksym-garkusha.github.io/energoreestr/)**. Дані там оновлюються щотижня.

Це незалежний навчальний проєкт на відкритих даних. Він не пов'язаний з НКРЕКП чи іншими державними органами і не замінює офіційні реєстри.

Регулятор публікує реєстри окремими CSV. Щоб відповісти на просте питання «що відомо про компанію з таким-то кодом», треба відкрити кілька файлів, і в кожному свої сюрпризи. Цей проєкт забирає файли з порталу, приводить їх до ладу, складає в SQLite і віддає двома способами: через HTTP API та як статичну сторінку пошуку.

Зараз підключено три набори:

| Набір | Що в ньому | Записів |
|---|---|---|
| [Реєстр учасників оптового енергетичного ринку](https://data.gov.ua/dataset/3ec102b6-7725-4b37-9a72-f502da845990) | хто має право торгувати електроенергією і газом на оптовому ринку | 3173 |
| [Природні монополії в енергетиці](https://data.gov.ua/dataset/ed63c78a-761f-4cc7-8e85-29d311135c5e) | оператори розподілу газу й електроенергії, транспортування | 57 |
| [Природні монополії в теплі та воді](https://data.gov.ua/dataset/7b662002-f5f3-4a1d-af43-2f68dc8acaf0) | теплові мережі, водоканали | 3522 |

Цифри за файлами, які лежали на порталі 16.11.2026.

## Що виявилося у файлах

Найбільше часу пішло не на API, а на те, щоб файли взагалі прочитати.

**Реєстр оптового ринку не читається стандартним парсером CSV.** Роздільник у ньому кома, але значення з комами не взяті в лапки. Назва органу реєстрації («Національна комісія, що здійснює державне регулювання...») стоїть у кожному рядку, тому заголовок обіцяє 20 колонок, а звичайний парсер бачить від 21 до 28. Жоден із 3173 рядків не має 20 полів. Excel відкриває такий файл без жодного попередження і просто зсуває колонки.

**У реєстрах монополій ЄДРПОУ збережено як число.** Нулі на початку зникли: Київгаз записаний як `3346331` замість `03346331`. В енергетичному реєстрі так у 29 записах із 57. Через це ті самі компанії не зводяться між реєстрами простим порівнянням кодів.

**Файл по теплу і воді це аркуш Excel, збережений як є.** Після семи колонок ідуть 67 порожніх, між записами стоять рядки з назвою області, нумерація в кожній області починається заново, 28 рядків повторюються.

Дрібніше, але теж заважає роботі з даними:

- 12 EIC-кодів не проходять перевірку контрольного символу, ще 4 не відповідають формату (мала літера, 15 символів замість 16, три коди в одному полі);
- 14 кодів ЄДРПОУ в реєстрі тепла і води не проходять перевірку контрольного розряду;
- у реєстрі оптового ринку в 73 словах змішано кирилицю і латиницю (`ВIДПОВIДАЛЬНIСТЮ` з латинською `I`). Майже половина з них це слово «Республіка» в назві країни, решта в назвах компаній, і звичайний пошук за назвою такі записи не знаходить;
- у полі для сайту трапляються e-mail, адреси з пробілами посередині та дефіс замість порожнього значення.

Повний перелік із номерами рядків: [docs/quality-report.md](docs/quality-report.md). Звіт збирається командою, тому його можна перегенерувати, коли на порталі з'явиться новий файл.

Ще одне спостереження. Портал зберігає заявлену періодичність оновлення, і її можна порівняти з фактичною датою файлу. Реєстр оптового ринку заявлено як щотижневий, а файл на день перевірки мав 42 дні. Це видно в `/api/datasets`.

## Що виправило б це в джерелі

Майже всі зауваження зі звіту зникають після чотирьох змін в експорті, і жодна з них не потребує міняти самі реєстри:

1. брати в лапки значення, в яких є кома або лапки (це вимога [RFC 4180](https://www.rfc-editor.org/rfc/rfc4180));
2. зберігати ЄДРПОУ як текст, щоб не губилися нулі на початку;
3. вивантажувати таблицю без порожніх колонок і рядків-заголовків областей, а область винести в окрему колонку;
4. перевіряти контрольний розряд ЄДРПОУ та EIC під час внесення запису.

Звіт із номерами рядків можна передати розпоряднику як є: за ним видно, які саме записи варто звірити.

## Як відновлюються колонки

Усе тримається на одному спостереженні: всередині значення після коми стоїть пробіл, а між колонками пробілу немає.

```
1,Національна комісія, що здійснює державне регулювання...,Україна,2023-10-19,...
                      ^ пробіл: це продовження             ^ без пробілу: нова колонка
```

Цього правила вистачає для 3133 рядків із 3173. У решті 40 воно дає не ту кількість колонок, наприклад коли сайт записали як `44524171, https://...` і він приклеївся до коду. Для таких рядків програма перебирає інші варіанти меж і бере той, де найбільше колонок схожі на себе: на місці дати стоїть дата, на місці EIC щось схоже на EIC, організаційно-правова форма написана звичайним реченням, а не великими літерами.

У 5 рядках із цих 40 однаково добре підходило кілька варіантів (незрозуміло, де закінчується вулиця і починається місто в іноземній адресі). Вони позначені в звіті як неоднозначні, решта полів у них розкладена правильно.

Код: [RowRepair.cs](src/Energoreestr/Csv/RowRepair.cs), перевірки колонок у [WholesaleParser.cs](src/Energoreestr/Registers/WholesaleParser.cs).

## Запуск

Потрібен [.NET 10 SDK](https://dotnet.microsoft.com/download/dotnet/10.0). Базу встановлювати не треба, SQLite це один файл поруч із програмою.

```bash
git clone https://github.com/maksym-garkusha/energoreestr.git
cd energoreestr/src/Energoreestr

dotnet run -- import      # забрати свіжі файли з data.gov.ua
dotnet run                # API на http://localhost:5256, там же сторінка з документацією
```

Інші команди:

```bash
dotnet run -- report                        # зібрати звіт про якість у quality-report.md
dotnet run -- export ../../site             # зібрати data.json для сторінки пошуку
dotnet run -- import wholesale файл.csv     # імпортувати файл із диска
dotnet test                                 # з кореня репозиторію
```

Повторний `import` нічого не качає, якщо файл на порталі не змінився. Щоб сервер сам перевіряв портал, у `appsettings.json` є `Import:IntervalHours`.

## API

| Запит | Що повертає |
|---|---|
| `GET /api/companies/{єдрпоу}` | усе про компанію з усіх реєстрів і зауваження до її записів |
| `GET /api/participants?q=` | пошук учасників оптового ринку за назвою, ЄДРПОУ, EIC або кодом реєстрації |
| `GET /api/participants/{ecrb}` | повний запис учасника |
| `GET /api/monopolies?q=&activity=` | пошук у реєстрах монополій |
| `GET /api/changes` | що з'явилося, зникло чи змінилося від файлу до файлу |
| `GET /api/quality` | скільки і яких зауважень до кожного файлу |
| `GET /api/quality/issues?code=` | самі зауваження з номерами рядків |
| `GET /api/datasets` | свіжість файлів на порталі проти заявленої періодичності |
| `GET /api/check/edrpou/{код}`, `/api/check/eic/{код}` | перевірка контрольного розряду |

Код компанії можна передавати з нулями і без: `/api/companies/100227` і `/api/companies/00100227` дадуть ту саму картку. Для Укренерго в ній запис з реєстру оптового ринку, записи з обох реєстрів монополій і зауваження, що в одному з файлів код записаний без нулів.

Пошук за назвою не залежить від регістру, виду лапок і латинських літер-двійників: `укренерго`, `«Укренерго»` і `УКРЕНЕРГО` шукають одне й те саме.

## Як влаштовано

```
src/Energoreestr/
  Csv/         читання CSV і відновлення зсунутих колонок
  Codes/       контрольні розряди ЄДРПОУ та EIC
  Text/        нормалізація назв для пошуку
  Registers/   розбір кожного реєстру і перелік видів зауважень
  Import/      клієнт data.gov.ua, імпорт, порівняння з попереднім файлом
  Data/        модель бази (EF Core, SQLite) і міграції
  Api/         ендпоінти
  Report/      звіт про якість у Markdown
  Export/      дані для сторінки пошуку одним JSON
site/          сторінка пошуку: один HTML-файл без збірки
tests/         xUnit, зразки зі справжніх рядків реєстрів
```

Кілька рішень, які варто пояснити.

**Історія змін.** Портал зберігає тільки останній файл, тому історію доводиться накопичувати самому. При імпорті новий файл порівнюється з тим, що вже лежить у базі, і різниця пишеться в журнал: хто з'явився, хто зник, яке поле змінилося і з чого на що. Перший файл у журнал не потрапляє, інакше там було б кілька тисяч «додано». Чесно: на справжніх даних журнал ще порожній, бо відтоді, як проєкт існує, файли на порталі не оновлювалися. Логіку порівняння перевіряють тести.

**Дані підприємців.** У реєстрах є ФОПи, і в колонці коду в них стоїть РНОКПП. У базу не потрапляють ні він, ні номер платника ПДВ (у підприємця це той самий номер), ні адреса. Лишаються ім'я, як воно стоїть у публічному реєстрі, і позначка, що це фізична особа-підприємець. На сторінку пошуку записи про підприємців не виносяться взагалі.

**Сторінка пошуку без сервера.** Раз на тиждень GitHub Actions запускає імпорт, складає всі компанії в один `data.json` (близько 300 КБ після стиснення) і викладає його разом зі сторінкою на GitHub Pages. Пошук працює в браузері. Для семи тисяч записів це простіше й надійніше, ніж тримати десь увімкнений сервер: нічого не може впасти й нічого не коштує. Записи про підприємців у цей файл не потрапляють.

**SQLite, а не PostgreSQL.** Даних близько семи тисяч записів, пише в базу один процес. Окремий сервер бази тут нічого б не дав, а запуск ускладнив би. Запити написані через EF Core, тож при переїзді на PostgreSQL їх міняти не доведеться, перегенерувати треба буде тільки міграції.

## Чого тут немає

- Перевірка контрольного розряду показує, що код підозрілий, але не каже, який правильний. Це може зробити тільки той, хто веде реєстр.
- Реєстр об'єктів відновлюваної енергетики не підключено: у ньому немає кодів, тільки назви, а зведення за назвами дає надто багато хибних збігів.
- API ніде не розгорнуто, запускається локально. Наживо працює тільки сторінка пошуку, і журналу змін на ній поки немає.
